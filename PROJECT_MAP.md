## 2. Tech Stack

- **Backend**: Python 3.9, Flask 3.0.3, Flask-WTF (CSRF), Flask-Mail, PyJWT, Werkzeug,
  openpyxl (Excel export), firebase-admin 6.5.0, requests, gunicorn (prod WSGI server).
  See `requirements.txt`.
- **DB**: SQLite (`finance_tracker.db`), accessed via raw `sqlite3` module (no ORM),
  WAL journal mode, manual schema migrations in `init_db()`.
- **Frontend**: Server-rendered Jinja2 templates, Bootstrap 5.3 + Font Awesome 6.4 (CDN),
  Chart.js (CDN) for graphs, vanilla JS (no framework/bundler for the web app itself).
- **Mobile**: Capacitor 8.x wrapping the same server-rendered web app in a native
  WebView shell (Android only configured; iOS paths referenced in `.gitignore` but no
  `ios/` directory exists). Plugins: `@capacitor/push-notifications`, `@capacitor/share`,
  `@capacitor/status-bar`.
- **Push**: Firebase Cloud Messaging, HTTP v1 API, OAuth2 via `google-auth`/`google.oauth2.service_account`
  (imported lazily inside `get_fcm_access_token()` — not in requirements.txt explicitly,
  comes transitively via `firebase-admin`/`google-auth`).
- **Auth**: Firebase Authentication (server-side only, via REST API + Admin SDK in
  `firebase_config.py`) backing a local `users` table; JWT (HS256) for the mobile/API
  layer; Flask session for the web layer.
- **Infra (production)**: `docker-compose-new.yml` — Traefik reverse proxy w/ Let's Encrypt,
  n8n automation, and two containerized Flask apps (`finance-app` legacy + `ourhome` new)
  behind different hostnames, VPS presumably at `matanshimonwebapp.online`.
- **Build tooling**: `npx cap sync android` (per `README.txt`) after IP/URL changes,
  Gradle for Android build (`android/gradlew`).

## 3. Entry Points

- **Flask dev server**: `python app.py` — runs `init_db()` then
  `app.run(host='0.0.0.0', port=int(os.environ.get('PORT', 5000)), debug=False)`.
  Note `init_db()` is ALSO called unconditionally at module import time (line ~2974,
  outside `if __name__ == '__main__'`), so it runs correctly under gunicorn too.
- **Production server**: gunicorn (listed in requirements.txt) behind Traefik per
  `docker-compose-new.yml`, container port 5000, env vars `DATABASE_PATH`,
  `SECRET_KEY`, `JWT_SECRET`, `FIREBASE_API_KEY`, `TZ=Asia/Jerusalem`.
- **Android app**: `android/` is a Capacitor project. `capacitor.config.json`
  `server.url` currently points at `https://new.matanshimonwebapp.online` (was a
  local IP `http://192.168.1.51:5000` before the uncommitted change — see §7) with
  `cleartext: true`. The WebView loads that URL directly; `www/index.html` is only a
  loading-shell fallback bundled into the APK, not the actual app. Build/run via
  Android Studio or `android/gradlew`; sync web changes into the shell with
  `npx cap sync android`.
- **Background threads started at import time** (daemon threads, no scheduler lib):
  - `_archive_thread` → `check_auto_archive()` (loop, sleeps 300s)
  - `_reminder_thread` → `check_feeding_reminders()` (loop, sleeps 60s)
  Both start unconditionally when `app.py` is imported — this means under gunicorn
  with multiple worker processes, these loops run once per worker (potential
  duplicate-processing risk; not accounted for in the code).

## 4. Core Modules / Functions (jump points)

All in `app.py` unless noted.

**Auth & session**
- `require_auth(f)` (~line 521) — web+API decorator; syncs `family_id` from DB,
  redirects to `family_setup` if user has no family (with an endpoint allowlist).
- `require_api_auth(f)` / `require_api_family(f)` (~304, 335) — JWT-only decorators
  for `/api/*` routes, populate `request.api_user`.
- `auto_jwt_auth()` (~117, `before_request`) — for any `/api/*` request, decodes
  Bearer JWT if present and populates BOTH `request.api_user` and the Flask
  `session` (so legacy session-based helpers keep working transparently).
- `create_jwt_token()` / `decode_jwt_token()` (~272, 286) — HS256, 30-day expiry
  (`JWT_EXPIRY_DAYS`), secret from `JWT_SECRET` env (falls back to `app.secret_key`).
- `is_admin()` (~44) — checks `is_admin` flag (system admin, not family admin).
- Family admin (the user who created the family, `families.created_by`) is a
  SEPARATE concept from system admin (`users.is_admin`) — checked ad hoc in several
  routes (e.g. `remove_family_member`, `leave_family`, `api_update_family_settings`).

**Firebase Auth layer** (`firebase_config.py`)
- `firebase_create_user`, `firebase_verify_login`, `firebase_send_reset_email`,
  `firebase_update_password`, `firebase_get_user` — thin wrappers around Firebase
  Admin SDK + Identity Toolkit REST API. All fail open/soft (never block local
  auth flow if Firebase is unreachable/misconfigured), except registration where a
  Firebase error IS surfaced to the user.
- Uses `serviceAccountKey.json` by default (`FIREBASE_CREDENTIALS_PATH` env
  overrides path; `FIREBASE_CREDENTIALS` env can hold the JSON inline instead).

**Billing cycle helpers** (~line 183-271)
- `get_cycle_day(family_id)` — reads `family_settings.cycle_day` (default 1).
- `get_cycle_month(family_id)` — current cycle's `'YYYY-MM'` label.
- `get_cycle_range(family_id)` — `(start_date, end_date, hebrew_label)` tuple.
- Both duplicate a Hebrew month-name dict inline in several places (`app.py` has at
  least 4 separate copies of `hebrew_months = {1:'ינואר', ...}` — in
  `get_cycle_range`, `check_auto_archive`, `history_data`, `history_month_detail`;
  not centralized as a module constant).

**Database**
- `get_db()` (~157) — opens a new `sqlite3.connect(DATABASE, timeout=10)` per call
  (`with get_db() as conn:` pattern everywhere), WAL mode, `busy_timeout=5000`.
- `init_db()` (~397) — idempotent `CREATE TABLE IF NOT EXISTS` for all 12 tables,
  followed by a manual `ALTER TABLE ... ADD COLUMN` migration loop (each wrapped in
  try/except `OperationalError` to no-op if the column exists), then creates
  performance indexes, then seeds the 9 default categories (`family_id IS NULL`).
  This is the entire "migration system" — no Alembic/Flask-Migrate.

**Push notifications** (~2484-2604)
- `FCM_SERVICE_ACCOUNT_PATH` — env `FCM_SERVICE_ACCOUNT` or defaults to
  `<app dir>/firebase-service-account.json` (a DIFFERENT file from
  `serviceAccountKey.json` used for Auth — see §7, this file is missing locally).
- `get_fcm_access_token()` — OAuth2 token via `google.oauth2.service_account`,
  cached in module-global `_fcm_credentials`, refreshed when expired.
- `get_fcm_project_id()` — reads `project_id` straight out of the service account JSON.
- `_send_push_worker(...)` — synchronous loop posting to FCM v1 REST endpoint per
  token, called on a background `threading.Thread`.
- `send_push_to_family(family_id, title, body, exclude_user_id=None)` — the single
  public entry point used everywhere; looks up tokens, spawns the worker thread
  (non-blocking so the HTTP response isn't delayed). Every "user did X" call site
  passes `exclude_user_id` so the actor doesn't get notified of their own action;
  system alerts (budget, feeding, auto-archive) omit it so everyone gets pinged.

**Schedulers (background daemon threads, no cron/Celery/APScheduler)**
- `check_budget_alerts(family_id)` (~2729) — called synchronously right after
  `add_payment`/`add_payment_api`; checks 80%/100% monthly threshold (dedup via
  `budget_alert_80_sent`/`_100_sent` storing the cycle month already alerted) and a
  simple daily-budget overage check (no dedup — can refire same day, appears
  intentional since it's a same-day amount check not a threshold-crossing check).
- `check_auto_archive()` (~2788) — infinite loop, sleeps 300s, iterates all
  `family_settings` rows, archives the previous cycle's payments once a new cycle
  has started (dedup via `last_cycle_archived` column), pushes a system notification.
- `check_feeding_reminders()` (~2877) — infinite loop, sleeps 60s, per family with
  `feeding_reminder_hours > 0`, finds latest feeding, and alerts once per
  `(feeding_id, hours_setting)` state (dedup via `last_alert_feeding_id` +
  `last_alert_hours` columns) — carefully documented in the function's own
  docstring to avoid spam on retroactive/edited feeding entries.

**Route groups** (grep `^@app\.route` in `app.py` for the full list — ~130 routes).
High-level groups, each with both a legacy session/web route and (for most
features added later) a parallel `/api/...` JWT route:
- Auth: `/login`, `/register`, `/logout`, `/forgot-password`, `/reset-password/<token>`,
  `/change-password` (web) mirrored by `/api/auth/login|register|me|refresh|
  change-password|forgot-password|reset-password` (JWT, all `@csrf.exempt`).
- Family: `/family`, `/family/create`, `/family/join`, `/api/family/remove-member`,
  `/api/family/leave`, plus `/api/family/info|create|join|settings|cycle`.
- Home/dashboard: `/`, `/home`, `/api/home-summary`, `/dashboard`, `/add_payment`,
  `/api/payments/add`, `/api/payments` (GET), `/api/payments/<id>` (PUT/DELETE),
  `/delete_payment/<id>`, `/archive_month`, `/api/payments/archive`,
  `/export_csv` (renders an XLSX via openpyxl despite the name!),
  `/api/payments/export` (this one really is CSV), `/api/chart_data`.
- History: `/history`, `/api/history/data`, `/api/history/month`.
- Categories: `/api/categories` (GET/POST), `/api/categories/<id>` (DELETE).
- Shopping list: `/shopping-list`, `/api/shopping-items` (GET/POST),
  `/api/shopping-items/<id>` (PUT/DELETE), favorites sub-routes
  (`/favorites`, `/add-favorites`, `/delete-favorite`, `/add-new-favorite`,
  `/edit-favorite`), `/api/shopping-items/clear-completed`.
- Recurring payments: `/api/recurring` (GET/POST/PUT/DELETE),
  `/api/recurring/<id>/add`, `/api/recurring/add-all`.
- Baby tracker: `/baby-tracker`, `/api/feedings` (POST), `/api/feedings/<id>`
  (PUT/DELETE), `/api/feedings/data`.
- Push: `/api/push/register`, `/api/push/unregister`.
- Settings: `/settings`, `/update-profile`, `/api/settings` (GET),
  `/api/settings/profile` (PUT), `/api/family/settings` (GET/PUT — budget,
  feeding_reminder_hours, cycle_day; cycle_day change is family-admin-only and
  triggers a live re-categorization of all non-archived payments into the new
  cycle boundaries).
- Admin: `/admin` → `admin_dashboard()` — system-wide KPIs (users, families,
  active families = 2+ members, registrations chart, payments-by-month chart,
  family-size breakdown) gated by `require_admin` (`users.is_admin`, not family
  admin).
- Misc: `/sw.js` (serves `static/sw.js`), CORS preflight catch-all
  `OPTIONS /api/<path:path>`.

## 5. Data Flow

**Web (browser/PWA) request**
`Browser → Flask route (session-based require_auth) → sqlite3 via get_db() →
Jinja2 render_template (server-rendered HTML) or jsonify (for the many pages that
fetch() their own data client-side, e.g. dashboard.html/home.html) → client JS
updates DOM / Chart.js.`

**Mobile (Capacitor) request**
`Android WebView loads capacitor.config.json's server.url (the SAME Flask server,
same Jinja2 templates, same JS) → base.html's fetch() calls to /api/... routes
mostly automatically include the JWT once login has run through /api/auth/login,
stored client-side by base.html/app JS (not shown in templates read here — token
storage is presumably in localStorage, not inspected in a JS file per se since
this app doesn't ship custom bundled JS beyond template <script> blocks) → Flask's
auto_jwt_auth before_request decodes the Bearer token → same route handlers as web,
because auto_jwt_auth also populates session so legacy session-reading code paths
"just work" for JWT-authenticated requests too.`
CSRF: enforced only for non-`/api/` POST/PUT/PATCH/DELETE (`check_csrf()`
before_request, ~107); `/api/*` is CSRF-exempt because it's Bearer-token protected.

**Push notification flow**
`User action (e.g. add_payment) → send_push_to_family(fid, title, body,
exclude_user_id) → SELECT push_tokens for family members (minus excluded user) →
background thread → get_fcm_access_token() (OAuth2 via firebase-service-account.json)
→ POST to FCM v1 REST API per token → Android system tray notification (via
Capacitor's registered MessagingService) even if app is closed.`
Token registration flow: `base.html` JS (only runs `if
window.Capacitor.isNativePlatform()`) → `PushNotifications.register()` → Capacitor
plugin fires native FCM token → JS `registration` listener → `POST
/api/push/register` → stored in `push_tokens` table keyed by `token` (unique),
mapped to `user_id`.

**Billing cycle flow**
`family_settings.cycle_day` (1-28, default 1) drives `get_cycle_month()`/
`get_cycle_range()` used everywhere payments are filtered/labeled → background
`check_auto_archive()` thread moves the previous cycle's `payments` rows to
`archived=TRUE` + inserts a summary row into `archived_cycles` once the current
cycle rolls over → `history.html`/`/api/history/*` read from `archived_cycles`
(with a label-parsing fallback for old rows lacking a `month` column) plus raw
`payments` for `archived=TRUE`.

## 6. Conventions

- **Family isolation**: virtually every query filters by `family_id` (or joins to
  a categories row that's either global `family_id IS NULL` or matches). No
  ORM-level enforcement — it's manual and consistent enough that
  `test_production.py`/`test_edge_cases.py` explicitly stress-test 3-family
  isolation.
- **ID casting**: user/family IDs from JSON bodies or session are frequently
  wrapped in `int(...)` before comparison (defends against string/int JSON
  mismatches) — e.g. `remove_family_member`, `api_update_family_settings`.
- **Error messages**: all user-facing strings are in Hebrew; error responses are
  `jsonify({'error': '...'}), <code>` with an optional stable `'code'` field
  (`AUTH_REQUIRED`, `TOKEN_INVALID`, `NO_FAMILY`, `USER_NOT_FOUND`,
  `ADMIN_REQUIRED`) for the mobile client to branch on.
- **Web vs API route pairing**: most features have a legacy session/web route
  (form POST + redirect + `flash()`) AND a parallel JSON `/api/...` route added
  later for the mobile app; logic is duplicated between the two rather than
  shared in a common function (e.g. `add_payment` vs `add_payment_api`, both do
  their own INSERT + push + budget check).
- **CSRF**: manual `@csrf.exempt` decorator on every `/api/*` view function
  (`WTF_CSRF_CHECK_DEFAULT = False`, enforcement done manually in `check_csrf()`),
  rather than a blueprint-level exemption — easy to forget on a new API route.
- **No blueprints/packages**: the entire backend is one file, one flat namespace
  of route functions; no `Blueprint`, no `app/` package structure.
- **No ORM/migrations tool**: raw SQL strings + manual `ALTER TABLE` try/except
  loop in `init_db()` serves as the migration mechanism.
- **Threading, not a task queue**: background jobs are plain daemon
  `threading.Thread` loops started at import time, not Celery/APScheduler/cron.
- **Testing**: no pytest fixtures/config — all three main test files
  (`test_production.py`, `test_edge_cases.py`, `test_flows.py`) are standalone
  scripts using `requests` against a live server (`BASE = 'http://127.0.0.1:5000'`),
  a hand-rolled `check(name, condition, detail)` counter, and direct sqlite3
  connections to `finance_tracker.db` for setup/verification. Run manually with
  Flask already running:
  ```
  python test_files/test_production.py
  python test_files/test_edge_cases.py
  python test_files/test_flows.py
  ```
  These tests run against the REAL dev database (not an isolated test DB) —
  `cleanup_db.py` exists specifically to purge the test/load users/families they
  leave behind.
