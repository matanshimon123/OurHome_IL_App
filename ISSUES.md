## Critical

### 1. `.gitignore` is UTF-16LE encoded — every ignore rule is silently inactive
- **Location**: `.gitignore` (repo root)
- **Severity**: Critical
- **Category**: Security / Git hygiene
- **Why it matters**: Confirmed directly with `file .gitignore` → `UTF-16, little-endian` and `git check-ignore -v serviceAccountKey.json` / `... finance_tracker.db` → both exit code 1 (not ignored). Git's ignore parser only understands the file as UTF-8/ASCII text, so every pattern listed (secrets, `*.db`, `node_modules`, `__pycache__`, etc.) is dead text — this is very likely the root cause of the two issues below, and means the next `git add -A`/`git add .` will silently re-stage the live Firebase credential and the production SQLite database.
- **Suggested fix**: Re-save `.gitignore` as plain UTF-8 (no BOM), verify with `git check-ignore -v` against each currently-tracked secret/DB file, then proceed to untrack the files below.

### 2. `finance_tracker.db` (+ `-shm`/`-wal`, + `test_files/finance_tracker.db`) are tracked in git
- **Location**: repo root and `test_files/`; confirmed via `git ls-files | grep finance_tracker.db`
- **Severity**: Critical
- **Category**: Security (PII exposure)
- **Why it matters**: Real family names, emails, and financial transaction data are committed into git history on every commit that touches these files, and the working copies are modified again right now. Anyone with repo access (including any prior collaborator, CI log, or fork) has permanent access to this data regardless of future deletion, since git history retains it.
- **Suggested fix**: `git rm --cached` the four files once `.gitignore` is fixed, then evaluate whether a full history scrub (like the one already done for `serviceAccountKey.json`) is warranted given real user data is involved.

### 3. `serviceAccountKey.json` (Firebase Auth Admin SDK credential) is one `git add` away from being recommitted
- **Location**: repo root, untracked (`git status` shows `?? serviceAccountKey.json`)
- **Severity**: Critical
- **Category**: Security (credential exposure)
- **Why it matters**: This exact filename was committed and scrubbed from history twice already (`git log --all -- serviceAccountKey.json` shows two removal commits, the second an explicit history rewrite), yet it sits in the working tree today with the `.gitignore` bug (#1) providing zero protection. If it is the same credential that was previously exposed in history before the scrub, it should be treated as already compromised regardless of the `.gitignore` fix.
- **Suggested fix**: Move the file out of the repo directory entirely (or load it via `FIREBASE_CREDENTIALS`/`FIREBASE_CREDENTIALS_PATH` env var pointing outside the working tree), and rotate the service account key in the Firebase console given its history of prior exposure.

### 4. Production secrets in `docker-compose-new.yml` are weak, unrotated placeholders — enables JWT forgery / full account takeover
- **Location**: `docker-compose-new.yml` lines 69, 87-89 (untracked); consumed by `app.py` lines 36, 40 (`SECRET_KEY`/`JWT_SECRET` env vars) and `firebase_config.py` line 25
- **Severity**: Critical
- **Category**: Security (secrets management / authentication bypass)
- **Why it matters**: The `ourhome` service — which serves the real production domain matching the app's own `capacitor.config.json` (`new.matanshimonwebapp.online`) — sets `SECRET_KEY=ourhome-il-secret-key-2026-change-me` and `JWT_SECRET=ourhome-il-jwt-secret-2026-change-me` in plaintext. These are not high-entropy secrets; the literal `-change-me` suffix confirms they were never rotated. `app.py`'s `create_jwt_token`/`decode_jwt_token` sign and verify with exactly this value using HS256. Anyone who reads this file (it will be committed the moment the `.gitignore` bug is fixed without care, or is already visible to anyone with VPS/deploy access) can forge a JWT for any `user_id` with `is_admin: true`, granting full read/write access to any family's data and the system admin dashboard. The `finance-app` legacy service in the same file also ships `DEFAULT_USER=admin`/`DEFAULT_PASS=admin`, a default-credential exposure on a still-routable hostname (`webapp.matanshimonwebapp.online`).
- **Suggested fix**: Generate cryptographically random secrets (`secrets.token_hex(32)`) for `SECRET_KEY`/`JWT_SECRET`, move them to a `.env` file or secrets manager excluded from the compose file, rotate immediately, and audit/decommission the legacy `finance-app` service or at minimum remove the default admin/admin credentials.

### 5. Stored XSS via unescaped user-controlled text rendered through `innerHTML` across multiple templates
- **Location**: `templates/baby_tracker.html` lines 436, 454, 501-504 (`f.notes`, fully unescaped); `templates/settings.html` line 439 (`c.name`, fully unescaped); `templates/dashboard.html` lines 452, 477 and `templates/shopping_list.html` lines 361, 411, 417, 418 (inline `onclick="..."` attributes built with `.replace(/'/g, "\\'")`, which escapes single quotes only, inside a **double-quoted** HTML attribute)
- **Severity**: Critical
- **Category**: Security (Stored XSS)
- **Why it matters**: Confirmed by reading the render code, not assumed. Two distinct sinks exist: (a) `baby_tracker.html`'s day-timeline tooltip, day-popup detail, and event-log detail all inject the feeding's free-text `notes` field directly into `innerHTML` with **no escaping call at all** (unlike the page's own `esc()` helper, which exists but isn't used here) — `<img src=x onerror=...>` typed into a feeding note executes for every family member who opens the baby tracker or the day popup, no click required. `settings.html`'s category list does the same for custom category names. (b) `dashboard.html` (payment `editPay`/recurring `editRecurring`) and `shopping_list.html` (item name/favorites `addOneFav`/`editFav`, and the `image` field rendered as a raw `<img src="${i.image}">`) build `onclick="fn('...')"` attributes where only `'` is escaped; a payment description, category name, shopping item name, or `image` value containing a `"` breaks out of the attribute (e.g. `x" onmouseover="alert(document.cookie)`) and injects an arbitrary handler. Since the session cookie is HttpOnly, the direct win isn't cookie theft — it's that injected script runs in the victim's authenticated origin and can silently `fetch()` any `/api/*` endpoint with the victim's cookies attached (add/delete payments, change family settings, remove members if the victim is family admin, exfiltrate financial data), i.e. persistent session-riding against any other family member (or an admin who happens to view the page).
- **Suggested fix**: Route every user-supplied string through the existing `esc()` (or Jinja's `|e`) before insertion into `innerHTML`, and stop building `onclick="..."` strings by hand — use `data-*` attributes plus `addEventListener` so no user text ever enters an HTML attribute or inline JS string at all.

## High

### 6. CSRF: `GET /delete_payment/<id>` performs a state-changing delete with no CSRF protection
- **Location**: `app.py` line 1189 (`@app.route('/delete_payment/<int:pid>', methods=['POST', 'GET'])`), interacting with `check_csrf()` at line 106-113
- **Severity**: High
- **Category**: Security (CSRF)
- **Why it matters**: `check_csrf()` only calls `csrf.protect()` for `POST/PUT/PATCH/DELETE`; `GET` requests are never checked, by design (GET shouldn't mutate). This route explicitly accepts `GET` and deletes a payment by ID scoped to the caller's session `family_id`. A third-party page can embed `<img src="https://prod-host/delete_payment/123">`; any logged-in victim who merely loads that page has their browser auto-attach the session cookie, and the deletion executes with zero interaction beyond a page visit. This is the only mutating route in the app reachable by GET (confirmed via `grep` across all `methods=[...]` declarations — every other POST/PUT/DELETE route requires the corresponding HTTP verb and is covered by `check_csrf()`).
- **Suggested fix**: Drop `GET` from the route's methods (keep `POST` only) and update any template link/button that currently calls it via a bare `<a href>` to use a `fetch()`/form POST instead.

### 7. No rate limiting on the local password fallback used by email-less accounts
- **Location**: `app.py` `api_login()` lines 2061-2081 (`/api/auth/login`), `api_register()` lines 2108-2144 (`/api/auth/register`)
- **Severity**: High
- **Category**: Security (authentication / brute force)
- **Why it matters**: `/api/auth/register` only validates email format `if email and not re.match(...)` — an empty email passes validation, so mobile-API registration without an email is genuinely possible today. For any such user, `/api/auth/login`'s username path finds `u['email']` empty and falls into `elif u and check_password_hash(u['password_hash'], password)` — a purely local comparison with **no throttling, lockout, or attempt counting anywhere in the app**. Every other login path (email + Firebase) benefits from Google's own `TOO_MANY_ATTEMPTS` server-side throttling; this fallback path has none, and combined with the 6-character minimum password policy, is realistically brute-forceable to a full account takeover of that family's financial/baby data.
- **Suggested fix**: Require a non-empty, verified email at registration (removing the email-less path entirely), or if the local fallback must stay, add attempt-count/lockout tracking (e.g. Flask-Limiter) specifically on this branch.

### 8. `firebase-service-account.json` (FCM credential) is absent from the working tree — push notifications are non-functional locally

- **Why it matters**: `get_fcm_access_token()` prints `FCM service account not found` and every `send_push_to_family()` call silently no-ops on this machine. Anyone testing push-notification-dependent features (budget alerts, feeding reminders, add/delete notifications) locally will see no failures in the HTTP response but nothing will ever arrive — a confusing false-negative during manual testing or QA.

### 9. Web `/login` has no fallback when Firebase verification fails — silent registration failures cause permanent lockout
- **Location**: `app.py` `login()` lines 653-685, `firebase_create_user()` in `firebase_config.py` lines 56-77
- **Severity**: Medium
- **Category**: Bug / availability
- **Why it matters**: `firebase_create_user` swallows every exception except `EmailAlreadyExistsError` and returns `(None, None)` — registration then proceeds to insert a fully-functional local user row with `firebase_uid=''`, and the user is told "נרשמת בהצלחה!" even though no Firebase account exists. The web `/login` route, however, unconditionally calls `firebase_verify_login(email, password)` first and only looks up the local user if that succeeds — there is no fallback to the local `password_hash` on this path (only `/api/auth/login`'s username-only branch has that fallback, and only when no email is on file). Any user whose Firebase registration silently failed, or whose Firebase account is later deleted from the console, can never log in via the web app again despite having a valid local password hash.
- **Suggested fix**: Either make Firebase registration failures hard-block registration (surface the error instead of continuing), or add the same local `check_password_hash` fallback to the web `/login` route that the API login already has.

### 10. Local password-reset flow is entirely dead code — `reset_token` is never generated anywhere
- **Location**: `app.py` `/reset-password/<token>` (lines 366-394), `/api/auth/reset-password` (lines 2229-2251), `reset_password.html`; `secrets` module imported at line 21 but never referenced
- **Severity**: Medium
- **Category**: Code smell / dead code
- **Why it matters**: Confirmed by grepping every reference to `reset_token` in `app.py`: it is only ever **read** (`WHERE reset_token=?`) and **cleared** (`SET reset_token=""`) — no code path anywhere generates and stores a non-empty token. `forgot_password()`/`api_forgot_password()` fully delegate to Firebase's own hosted `accounts:sendOobCode` reset flow instead. This means the app's own token-based reset routes and template can never succeed through normal use; they are vestigial from an earlier design and could mislead a future maintainer (or security reviewer) into auditing/trusting a reset mechanism that is actually unreachable, while the real reset flow (Firebase's hosted page) lives entirely outside this codebase's control.
- **Suggested fix**: Either remove the unreachable local reset routes/template/columns, or finish the implementation (generate a `secrets.token_urlsafe()` value with an expiry on `forgot_password`) if a non-Firebase reset path is actually wanted as a fallback.

### 11. No route exists to delete a family or transfer admin ownership — a solo family creator can never leave
- **Location**: `app.py` `leave_family()` lines 1020-1030; confirmed via repo-wide grep that no `delete_family`/transfer-ownership route exists anywhere
- **Severity**: Medium
- **Category**: Bug / UX dead-end
- **Why it matters**: `leave_family` unconditionally blocks the family creator with `'Admin cannot leave. Delete family or transfer ownership first.'`, but neither alternative exists in the codebase. `remove_family_member` also blocks self-removal. A user who creates a family by mistake (e.g., meant to join via invite code instead) is permanently stuck as a member of that family with no in-app path out, short of direct database intervention.
- **Suggested fix**: Add a "delete family" route usable only when the caller is the sole member, and/or an "transfer admin" route, and only then allow `leave_family` to succeed for an admin.

### 12. `/api/recurring` POST/PUT skip input validation present on the equivalent payment endpoints
- **Location**: `app.py` `add_recurring()` lines 1817-1825, `update_recurring()` lines 1835-1842, contrasted with `add_payment_api()` lines 1120-1147 which validates
- **Severity**: Medium
- **Category**: Error handling / data integrity
- **Why it matters**: Both routes index `data['description']`/`data['amount']` directly with no `.get()` default and no numeric/positivity check. A request missing either key raises an unhandled `KeyError` → generic 500. A request with a non-numeric `amount` (e.g. a string) is accepted and stored (SQLite type affinity permits it), and later breaks any consumer that does `float(r['amount'])` — e.g. `add_recurring_to_month()`'s push-notification text (`f'... ₪{float(r["amount"]):.0f}'`) will itself throw a 500 the next time that recurring item is applied to a month, and category/monthly `SUM(amount)` aggregates silently ignore the bad row instead of surfacing the error.
- **Suggested fix**: Mirror `add_payment_api`'s validation (`.get()` with defaults, `float(amount) > 0` check, non-empty description) in both `add_recurring` and `update_recurring`, and make `update_recurring` support partial updates the same way `update_payment` does.

### 13. `add_feeding` can 500 *after* the DB write already committed
- **Location**: `app.py` lines 1901-1930
- **Severity**: Medium
- **Category**: Error handling / data integrity
- **Why it matters**: The `INSERT INTO feedings` happens inside its own `with get_db()` block and commits before the function composes the push-notification text with `int(amount_val)`. If the client sends a non-numeric `amount` (nothing validates its type), `int(amount_val)` raises `ValueError` *after* the feeding row is already persisted, so the client receives a 500/error even though the write succeeded — a plausible source of accidental duplicate feeding entries if the client retries on error.
- **Suggested fix**: Validate/coerce `amount` to a number before the INSERT (reject or default to 0 on failure), and wrap the notification-composition step so a formatting error can never surface as a request failure once the write has committed.

### 14. Inconsistent JSON body parsing safety between older and newer API layers
- **Location**: e.g. `add_category` (968), `add_shopping_item` (1650), `update_shopping_item` (1674), `add_feeding` (1905), `add_recurring` (1821) all call bare `request.get_json()`, versus the JWT/mobile endpoints added later (e.g. `api_login` 2052, `api_register` 2111, `api_update_family_settings` 2643) which consistently use `request.get_json(silent=True) or {}`
- **Severity**: Medium
- **Category**: Error handling / architecture consistency
- **Why it matters**: The two families of API routes handle malformed/empty JSON bodies differently. The newer pattern degrades gracefully to `{}` and returns a clean validation error; the older pattern will raise on a body Flask can't parse in some content-type/encoding combinations, or (as in finding #12) on a well-formed-but-incomplete body, producing an unhandled 500 instead of a friendly 400. This is the "duplicated logic between paired routes can drift" risk called out in the project map, made concrete.
- **Suggested fix**: Standardize every mutating route on `request.get_json(silent=True) or {}` plus explicit field validation, regardless of which "generation" of the API it belongs to.

### 15. Daily budget alert has no dedup — refires on every payment once the threshold is crossed
- **Location**: `app.py` `check_budget_alerts()` lines 2767-2777
- **Severity**: Medium
- **Category**: Bug / notification spam
- **Why it matters**: The monthly 80%/100% checks dedup via `budget_alert_80_sent`/`budget_alert_100_sent` (a cycle-month marker), but the daily-budget check has no equivalent state and simply re-sends `'💸 חריגה מהתקציב היומי!'` every single time `check_budget_alerts` runs after the daily total already exceeds `budget_daily`. A family that adds several small expenses after crossing their daily budget gets a duplicate push for every one of them, which will read as a broken/spammy feature rather than a deliberate design choice.
- **Suggested fix**: Add a `budget_alert_daily_sent` column keyed by date (mirroring the monthly pattern) so the daily alert also fires at most once per day.

### 16. FCM push worker never prunes invalid/unregistered tokens
- **Location**: `app.py` `_send_push_worker()` lines 2528-2563, `push_tokens` table
- **Severity**: Medium
- **Category**: Performance / data hygiene
- **Why it matters**: The worker POSTs to FCM per token and only catches/logs a generic exception on request failure — it never inspects the response body for FCM's `UNREGISTERED`/`INVALID_ARGUMENT` error codes that indicate a token is permanently dead (uninstalled app, revoked token, etc.). Dead rows accumulate forever in `push_tokens`, and every future push notification (for every event type in the app) keeps paying the network cost of contacting FCM for tokens that will never succeed again.
- **Suggested fix**: Parse the FCM response per token; on an `UNREGISTERED`/`NOT_FOUND` error, delete that row from `push_tokens` in the same worker pass.

### 17. `_fcm_credentials` module-global OAuth2 cache is mutated without a lock from concurrent threads
- **Location**: `app.py` `get_fcm_access_token()` lines 2492-2515, `_fcm_credentials` global at line 2489
- **Severity**: Medium
- **Category**: Concurrency / architecture
- **Why it matters**: `send_push_to_family` spawns a new background thread per call (add-payment, add-feeding, budget alert, auto-archive, etc. can all trigger this concurrently). Each thread's call to `get_fcm_access_token()` reads-checks-and-writes the same module-global `_fcm_credentials` object with no lock. Two threads can simultaneously find it `None`/invalid, both construct a fresh `Credentials` object and call `.refresh()`, doing redundant network round-trips and racing to overwrite each other's reference — not fatal, but wasteful and a source of hard-to-reproduce intermittent push failures under load.
- **Suggested fix**: Guard the read-check-refresh-write sequence with a `threading.Lock`.

### 18. Session and CSRF cookies are set with no explicit `Secure`/`SameSite` attributes
- **Location**: `app.py` — no `SESSION_COOKIE_SECURE`/`SESSION_COOKIE_SAMESITE` config anywhere; `inject_csrf_token()` lines 63-66 calls `response.set_cookie('csrf_token', generate_csrf())` with no flags
- **Severity**: Medium
- **Category**: Security (hardening gap)
- **Why it matters**: Confirmed by grep — the app never sets these Flask config keys, so Flask's defaults apply (`SESSION_COOKIE_SECURE=False`). The project's own history shows the Capacitor app was recently configured against a plain-HTTP LAN IP with `cleartext: true` (per `capacitor.config.json`'s prior value), i.e. this app has genuinely been served over unencrypted HTTP in practice, at which point neither the session cookie nor the CSRF cookie has any protection against network interception since `Secure` was never required.
- **Suggested fix**: Set `SESSION_COOKIE_SECURE=True` and `SESSION_COOKIE_SAMESITE='Lax'` (and the same flags on the manual `csrf_token` cookie) once the app is only served over HTTPS in every environment it's tested against.

### 19. `mail.send()` has no explicit SMTP timeout — can hang a request thread indefinitely
- **Location**: `app.py` `change_password()` lines 762-779, `api_change_password()` lines 2195-2212; `app.config['MAIL_*']` block lines 52-59
- **Severity**: Medium
- **Category**: Error handling / availability
- **Why it matters**: Flask-Mail's underlying `smtplib.SMTP` connection is opened with no timeout configured anywhere in this app, and Python's `smtplib` default is to block forever if the socket doesn't timeout. If `smtp.gmail.com` becomes unreachable or slow to respond once `MAIL_USERNAME`/`MAIL_PASSWORD` are eventually configured in production, the request thread handling a password change blocks indefinitely — under a threaded/sync WSGI worker model this can exhaust available workers under modest concurrent load, turning a mail hiccup into a site-wide outage.
- **Suggested fix**: Configure an explicit socket timeout for the mail connection (Flask-Mail supports passing connection options), or move the send onto a background thread the way push notifications already are.

### 20. Background daemon threads are not safe for multi-worker deployment
- **Location**: `app.py` lines 2869-2871 (`_archive_thread`), 2969-2971 (`_reminder_thread`); both started unconditionally at module import
- **Severity**: Medium
- **Category**: Architecture / operability
- **Why it matters**: `check_auto_archive()` and `check_feeding_reminders()` start as soon as `app.py` is imported, with no leader-election or single-instance guard. Under gunicorn with more than one worker process (the requirements.txt includes gunicorn, and this is the intended production WSGI server per the compose file), every worker runs its own independent copy of both loops against the same SQLite database — the dedup columns (`last_cycle_archived`, `last_alert_feeding_id`/`last_alert_hours`) reduce but don't eliminate the risk of two workers racing to archive the same cycle or send duplicate feeding-reminder pushes in the same tick, and each additional worker linearly multiplies the constant background query load against SQLite.
- **Suggested fix**: Gate these threads behind a single-worker check (e.g. only start when `os.environ.get('WEB_CONCURRENCY', 1) == '1'` or a file/DB lock), or move them to a proper single-instance scheduler (cron hitting an internal endpoint, or APScheduler with a documented single-worker requirement).

### 21. Missing security regression tests: JWT forged with a wrong/no secret, and CSRF actually blocking a request
- **Location**: `test_files/test_edge_cases.py` (only test near JWT is a garbage string `'not.a.jwt'` at line 196); no `csrf`/`CSRF` string appears anywhere in the file
- **Severity**: Medium
- **Category**: Test coverage
- **Why it matters**: Given `JWT_SECRET` falls back to `app.secret_key`, which itself falls back to a hardcoded default if `SECRET_KEY` is unset (`app.py` lines 36, 40), and given finding #4 above (weak deployed secret), a token signed with a different/predictable secret is exactly the attack this app is most exposed to — yet nothing in the suite constructs a JWT with `pyjwt.encode(payload, 'wrong-secret', algorithm='HS256')` and asserts it's rejected. Likewise, `check_csrf()`/`csrf.protect()` is core to every web (non-`/api/`) mutating route, but no test ever POSTs to a web route without a CSRF token and asserts a 400 — meaning a regression that accidentally disabled CSRF globally would go completely unnoticed by the existing suite.
- **Suggested fix**: Add one test that forges a JWT with a wrong secret and expects 401 from a protected endpoint, and one that POSTs to a web-form route (e.g. `/add_payment`) without the CSRF cookie/header and expects a 400.

### 22. Missing business-logic test coverage: budget-alert dedup state, feeding-reminder dedup state, cross-family write authorization
- **Location**: `test_files/test_edge_cases.py` lines 467-494 (budget alerts only assert `s == 201` on the add-payment calls, never inspect `budget_alert_80_sent`/`budget_alert_100_sent`); `test_files/test_production.py` (payments/recurring: only same-family CRUD success is tested, e.g. lines 208-232, 318-335 — no test has User C attempt to `PUT`/`DELETE` a payment or recurring-payment ID that belongs to Family 1); no test anywhere exercises `check_feeding_reminders()`'s `last_alert_feeding_id`/`last_alert_hours` state machine
- **Severity**: Medium
- **Category**: Test coverage
- **Why it matters**: These are exactly the areas `CLAUDE.md`/the project map flag as having "subtle state machines" — the budget test crosses both the 80% and 100% thresholds but never confirms a *second* payment past the same threshold doesn't re-alert, so a dedup regression would pass CI silently. Category, shopping-item, and feeding **read**-isolation between families is tested, but the corresponding **write** authorization (can family C delete/update family A's payment or recurring payment by guessing/incrementing an ID?) is never attempted even though the code path is correctly scoped by `family_id` — so this is currently safe but unverified by any regression test.
- **Suggested fix**: After crossing the 80%/100% thresholds, add a payment that keeps the family over budget and assert no *second* push fires (inspectable via the `family_settings` table directly, as the test files already do direct sqlite3 access elsewhere); add a same-shaped cross-family write test for `/api/payments/<id>` and `/api/recurring/<id>` (expect 404/403, not 200).

### 25. Fragile whitelist-driven dynamic SQL column pattern
- **Location**: `app.py` `update_payment()` line 1172, `update_shopping_item()` line 1678
- **Severity**: Low
- **Category**: Code smell (latent risk)
- **Why it matters**: Both routes build `f'UPDATE ... SET {f}=? WHERE id=? AND family_id=?'` where `f` is drawn from a hardcoded `allowed = [...]` list, not from the request body's keys — today this is **not** SQL-injectable since column names never come from user input. However, the code shape (loop variable named after the field, checked against `data`) looks exactly like the kind of code a future refactor could "simplify" into iterating `data.keys()` directly, silently introducing SQL injection with no visible change to the tests.
- **Suggested fix**: Replace the dynamic `f'{f}=?'` construction with an explicit `if/elif` per allowed field, or a dict mapping field name → parameterized SQL fragment, so there's no dynamic string interpolation into SQL text at all, even from a safe source.
